# Fee keeper

`run-keeper.sh` runs the fee pipeline in one pass: sweep → flush → relay (claim + retire) → convert → cushion. Its header documents the env contract and each step. `zeracle-keeper.service` runs it once, and `zeracle-keeper.timer` schedules that run.

## Decision record: 2026-09-25 (ZER-16)

The owner decided these on 2026-09-25, closing readiness review §10 item 5 (`testnet-readiness-review.md`) for the Pi chain host. The Pi is the only host the keeper runs on today; the retired EC2 box never ran it.

| Question | Decision | Why |
|---|---|---|
| Operator | The Pi chain host itself: systemd, installed by `pi/provision-pi.sh` and wired into `pi/deploy-pi.sh` | The Pi isn't a live network, so the owner rule against agent deploys to live networks doesn't apply there |
| Service user | `admin` | Same user as the Pi's chain-server and block-producer drop-ins, and the one that runs deploys. Root-owned stores broke Pi redeploys, and a dedicated keeper user would bring that ownership split back |
| Key | Anvil #4 (`0x15d3…6A65`) | The sandbox keeper key `run-keeper.sh` already documents. It is never #0 (the sequencer's) and never #1–#3 (the deployer, guardian and governance keys). Here that separation is by convention: `run-keeper.sh`'s deployer-key guard only fires when a deployer key is in its environment, and `keeper.env` sets none |
| Cadence | Daily (`OnCalendar=daily`, up to 15 min random delay, `Persistent=true`) | There's no proof window to race (below), so cadence only sets how stale unconverted fees get |
| Claim wait | `KEEPER_CLAIM_WAIT_SECS=1800` on the Pi | The Pi proves each block as it lands, so a witness normally appears within a block or two. A missed claim is retried on the next run |
| Pending expiry | `PENDING_FLUSH_MAX_AGE_SECS=2592000` (30 days) on the Pi | The default of 7200 would drop hashes that are still claimable (below) |
| State after a fresh chain | `deploy-pi.sh`'s first-run branch deletes `/var/lib/zeracle-keeper/pending-flush` and `/etc/zeracle/keeper.env` | A fresh chain makes every pending L2 hash meaningless; each would otherwise cost a full claim wait per run until it expired. The env names the old chain's token. Until the deploy succeeds and writes a new one, the unit's `ConditionPathExists=` skips every run |
| Pausing | `deploy-pi.sh` (resume) and `e2e-pi.sh` stop the timer, then **wait** for a run in flight (`pi/keeper-ctl.sh`, up to 1 h) | Killing a run mid-flush loses the flush hash (below) |
| Alerting | None yet: see "Open gap" | No alert channel exists |

The env file `/etc/zeracle/keeper.env` is generated by `pi/gen-keeper-env.sh` from the deployment manifest on every deploy and resume. `ZRCL_ADDRESS` changes with every fresh chain, so a hand-written file would go stale.

The env file also pins every contract address the keeper uses from the manifest: FeeDistribution, TokenPortal, LiquidityPool, MockDexAggregator and the three fee funds. The repo's deployment files aren't a safe source on the Pi, because `make sync-pi` ships the laptop's `v1-l1/deployments/*.json` over the Pi's. On 2026-09-25, the first keeper run after a sync converted and cushioned against a pool address that had no code.

## Measured: no ~2 h proof window on Aztec 5.2.0

`run-keeper.sh`'s header (ZER-13) assumes the node serves L2→L1 message proofs for "roughly 2 h", tied to world-state retention (`WS_NUM_HISTORIC_CHECKPOINTS`, default 64). That assumption set the weekly-floor trade-off and the 7200 s expiry default.

On the Pi on 2026-09-25, `getL2ToL1MembershipWitness` returned a witness for a message 14.7 h and 735 blocks old. The 5.2.0 node builds the witness in `archiver/dest/modules/outbox_trees_resolver.js` from the archiver's stored blocks plus the Outbox roots it reads from L1. Pruned world state isn't involved, so the witness stays available as long as the archiver keeps the block.

This matches ZER-59, which found that world-state pruning breaks historical state reads only.

**Not yet verified on a public Aztec node.** A testnet node could be configured to prune its archiver. Check this there (ZER-19) before changing `run-keeper.sh`'s 7200 default for testnet.

## Open gap: alerting

`zeracle-keeper.service` has no `OnFailure=`, because no alert channel (webhook, email, pager) exists. The plan rules out inventing one.

`run-keeper.sh` exits non-zero only on a genuine step failure; an idle run exits 0. So once a channel exists, every `OnFailure=` trigger is worth a notification. Until then:

- `systemctl list-units --failed` shows a failed last run.
- `journalctl -u zeracle-keeper` holds each run's summary block.
- `journalctl -u zeracle-keeper | grep EXPIRED` finds dropped hashes, which exit 0 and never fail the unit.

## Operating it on the Pi

```bash
systemctl list-timers zeracle-keeper.timer      # next and last run
sudo systemctl start zeracle-keeper.service     # run now (blocks until done)
journalctl -u zeracle-keeper -n 60 --no-pager   # last run's output and summary
cat /var/lib/zeracle-keeper/pending-flush       # flushes waiting to be relayed
```

`sudo systemctl start zeracle-keeper.service` while a run is in flight joins that run and waits for it. Only running `run-keeper.sh` by hand hits its lock (`/var/lib/zeracle-keeper/lock`) and aborts at once.

**Never `systemctl stop zeracle-keeper.service` on a live chain.** `run-keeper.sh` records a flush in `pending-flush` only once `flush-fees.ts` returns with the receipt, which takes minutes on the Pi. A stop in that window lets the submitted flush mine unrecorded, and nothing then claims those fees from the L1 Outbox. Stop the timer and wait instead: `pi/keeper-ctl.sh`'s `keeper_quiesce` does exactly that.

`pi/e2e-pi.sh` pauses the keeper that way before its fee round-trip, because otherwise the keeper could sweep the fees the test is about to flush. It restarts the timer on exit if the timer was running before, or if a deploy it made succeeded.

## A future testnet ops host

These decisions cover the Pi only. A testnet host still needs:
- its own operator and user;
- a purpose-generated, low-value Sepolia key, whose custody is kept apart from the deployer key;
- the testnet env block from `run-keeper.sh`'s header;
- a cadence decided after ZER-19 has checked the proof window on a real node.
